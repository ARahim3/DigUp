# Han filename lookups

`輔導` should find `學生情緒輔導紀錄.pdf` even before its contents have been embedded. FTS5's unicode61 tokenizer
keeps an unspaced Han run as one token, so matching the middle of that run needs a basename lookup.

```
query contains a run of at least two Han characters
  → literal SQLite prefilter over existing name rows
  → every query component must occur in the normalized basename
  → complete basename/stem, then partial basename, then existing content/meaning matches
```

The prefilter uses a bound `instr` argument, not LIKE wildcards. Names retain the existing NFKC normalization;
verification is case-insensitive and includes mixed letters, numbers and extensions. File-kind filters apply before
matches are ranked. A filename lookup points to its name segment, rather than an unrelated semantic page in that file.
Scores remain descending so the existing weaker-results fold can use them.

There is no schema change, index rebuild, embedding change, or new dependency. Existing names are immediately
searchable, including pending files, and moves/deletes are read from the live index. Latin-only queries and code
identifier search keep their existing rules. This does not introduce Chinese content tokenization, Traditional/
Simplified conversion, single-character substring lookup or Spotlight application/system actions.

## Reproduce the focused evaluation

Use a new, isolated folder and index:

```sh
python3 scripts/testbed/make_han_filenames.py /tmp/DigUpTestbed/han-filenames
.build/release/digup index /tmp/DigUpTestbed/han-filenames --limit 0 --index /tmp/DigUpHanIndex
DIGUP_TESTBED=/tmp/DigUpTestbed .build/release/digup eval evals/han-filenames.json --index /tmp/DigUpHanIndex
```

`--limit 0` syncs the actual fixture names without embedding their contents. This isolates filename recall from the
model's guesses. Use the same index for the before/after binaries; the file generator contains only synthetic text.

## Validation (macOS, Apple M2 Pro, 16 GB)

Compared official v0.6.1 with this patch on the same indexes and model. Nine regression tests cover two-character and
internal substrings, typing/settled queries, exact-name ranking, semantic-page competition, duplicate prevention,
kind filters, all query components, existing names, rename/delete, full-width/case normalization, code isolation, and
an exact name inserted after 1,100 partial matches. `swift test`: 101 passed (95 DigUpKit, 6 LlamaRuntime including
actual reference vectors).

| --- | ---: | --- | --- |
| Han names, keywords only | 12 | .33 / .33 / .33 | 1.00 / 1.00 / 1.00 |
| Upstream synthetic | 37 | .92 / .97 / .97 | .92 / .97 / .97 |
| Upstream multilingual | 48 | .92 / .98 / .98 | .92 / .98 / .98 |
| Upstream code | 41 | 1.00 / 1.00 / 1.00 | 1.00 / 1.00 / 1.00 |

All 126 upstream queries produced byte-identical evaluation output before and after. The synthetic/media/code
fixtures were generated by the upstream testbed scripts; the personal-file sampling step was omitted. These
figures are measured results on this fixture, not a claim of perfect recall across arbitrary files or languages.

A separate keyword-only index held 20,000 synthetic filenames, including 2,000 matching Han names. Twenty measured
CLI runs per query alternated before/after after two warmups; times include process startup, opening the same index
and returning up to 20 results. The extra basename verification costs time only for Han queries.
